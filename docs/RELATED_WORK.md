# 関連研究と、ロボもりの位置づけ

この資料は、ロボもりに近い先行研究、コードを読んで分かった限界、研究として次に確かめることをまとめたものです。

- 文献の書誌情報（題名・著者・誌名・年・DOI）は、2026-10-25〜26 に Crossref、arXiv、各出版社・SEI・NIST・AISI のページで確かめました。
- 中身の説明は、要旨（abstract）か、公開されている本文に基づきます。要旨を読めなかった文献は、題名と書誌から分かる範囲だけを書いています。
- コードについての記述は、`feature/m5-bluesky-link` ブランチの実装を読んで確かめたものです。
- 新しさについては、まだ仮説の段階です。網羅的な先行研究の調査で確かめる必要があります。

## 1. ロボもりの研究としての核

ロボもりの研究上の価値は、故障を見つけることそのものでも、複数ロボットへの仕事の配り直しそのものでもありません。**不確かな故障の情報を、安全の制約がついた「作業の許可」に変える部分**にある可能性が高い、と考えています。

今の実装の流れは次のとおりです。

1. **M5StickS3（BMI270）**：約 170 Hz で加速度を測り、重力を除いた揺れの RMS を 1 秒ごとに送る
2. **センサー中継（Python の `Judge`）**：300 mg 以上が 2 回続いたら Warning、6 回続いたら Limited、値が途切れたら Hold
3. **Unity（`GuardianCapabilityPolicy`）**：ロボットの状態 × 仕事の種類で、許すかどうかを決める
4. **配り直し**：許されなくなった仕事だけを取り消し、別のロボットに移す

ここに、研究として一番大きな飛躍があります。「300 mg 以上の揺れが続いた」ことは測れても、そこから「このロボットは皿の回収なら安全にできる」とは、その情報だけでは言えません。今の許可の表は、作業の**名前**で決めた固定の表です。

| 状態 | スープ | 料理 | 空いた皿 |
|---|---|---|---|
| Normal | 許可 | 許可 | 許可 |
| Warning | 禁止 | 許可 | 許可 |
| Limited | 禁止 | 禁止 | 許可 |
| Hold | 禁止 | 禁止 | 禁止 |

デモには分かりやすい表ですが、研究としては、この表が正しいことを実測で示す必要があります。空いた皿でも、高く積んである、濡れて滑りやすいといった場合は揺れに弱くなります。料理でも、ふたのある容器ならスープより安全なことがあります。**作業の名前ではなく、その作業が求める物理的な能力と安全の条件から許可を導く**ことが、次の研究の方向です。

## 2. 関わる研究領域

| 研究領域 | ロボもりで対応するところ |
|---|---|
| 故障に強いロボット（Fault-Tolerant Robotics） | 不調でも、できる仕事は続ける |
| 予知保全・健全性管理（PHM） | 外付けの IMU で揺れを測り、不調を見つける |
| しなやかな複数ロボット系（Resilient Multi-Robot Systems） | 複数のロボットのあいだで仕事を配り直す |
| 実行時の安全保証（Runtime Assurance） | 危ない仕事を、動いている最中に制限する |
| 機械の安全工学・規格 | 「仕事を続けてよいか」の判断と、「安全に止める」機能を分ける |
| 人間工学（自動化への信頼） | 戻すことと外へ出すことを、人が承認する |
| サイバーフィジカルセキュリティ | ネットから届く不正な指示を締め出し、記録を守る |

規格がどこまで当てはまるかは、ロボットの用途と構成で決まります。大事なのは、**「この仕事を続けてよいか」という上位の判断と、「機械を安全に止められる」という下位の安全機能を分ける**ことです。ロボもりは前者を受け持ち、後者は今ある安全制御（非常停止、衝突防止、速度制限）が受け持ちます。この責任の分け方を崩さない設計にします。

AISI の 9 つの観点と、ロボもりで確かめることの対応は次のとおりです。

| AISI の評価観点 | ロボもりで確かめること |
|---|---|
| 物理的安全性 | 衝突、転倒、荷物の落下、安全な停止 |
| 運用合理性 | その場に合った減速・待機・代わりの行動 |
| 安定性 | 状態が変わったときの急加速や不自然な動き |
| 人間の適切な介在 | 戻す承認、停止、人の負担、再開の条件 |
| プライバシー保護 | 記録を誰に出し、誰が読めるか |
| 説明可能性 | なぜその仕事を禁止したか |
| 検証可能性 | センサーの値・制御の指示・人の操作の記録を後から追えるか |
| 認知・判断の妥当性 | 床の問題と機体の故障を見分けられるか |
| インタラクションの適切性 | 現場の人が判断を理解できるか |

## 4. 先行研究との重なり

| 研究の要素 | 先行研究 | ロボもりの今 |

| 性能の劣化とスケジューリング | ある（Zhou 2024 ほか） | 続いた回数で状態を分ける |
| 故障の検知と割り当て直しの統合 | ある（Haider 2026、Cline 2026） | 実装済み |
| 劣化したあと修理に回す時期 | ある（Yan 2026） | 今後の展望 |
| 運ぶ物の物理的な安全から許可を決める | 個別の研究はある（Medico 2026 ほか） | まだ実証していない |
| 外付けの計測から、安全にできる仕事を決める | 周辺の研究はある | **ロボもりの有望な研究課題** |

最後の 2 つを「世界初」とは、今の段階では言えません。言えるのは、**実験に裏付けられた研究としてまとめる方向が見えている**ということです。

## 5. コードを読んで分かった、確かめるべき点

脆弱性が実証されたという意味ではありません。実装から読み取れる、まだ確かめていないリスクと設計上の制約です。

| 優先度 | 実装 | 問題になりうる点 |
|---|---|---|
| 高 | `Judge.on_key2()`（[`sensor_bridge.py`](../scripts/sensor_bridge/sensor_bridge.py)） | 確かめているのは、センサーの値が新しく届いているかだけ。**揺れが大きいままでも、通信が正常なら Normal に戻せる** |
| 高 | 2 回・6 回の連続超過の判定 | 異常が続いたことは分かるが、短い時間で起きる転倒や落下に間に合う保証はない |
| 高 | 1 秒の窓の RMS | 短い衝撃や、特定の周波数に弱い荷物の動きを見分けられない |
| 高 | 判定に使う値 | ファームウェアは `vib_rms_g` のほかに `vib_peak_g`・`ratio`・`tilt_deg` も送っているが、判定に使っているのは `vib_rms_g` だけ。**測れている情報を、まだ使っていない** |
| 中 | 重力を追う移動平均（`GRAVITY_ALPHA = 0.02`、170 Hz で約 0.3 秒） | 重力だけでなく、ゆっくりした走行の加速度も追ってしまう。揺れの RMS が小さくても、旋回や減速で荷物にかかる力が小さいとは限らない。スープでは特に大事 |
| 中 | 「何回続いたか」で数える判定 | 何秒続いたかではない。測る窓を 1 秒から 0.5 秒に変えると、同じ 6 回でも意味する時間が半分になる |

| 中 | シリアルの入力 | センサーの `seq` と `t_ms` は記録に残すが、サンプルの順番や新しさの厳密な検証には使っていない |
| 中 | 監視 AI（[`monitor.py`](../scripts/guardian_hub/monitor.py)） | 同じ場所で複数台が揺れたら床の問題と推定するが、因果関係を確かめたわけではない |

### KEY2 で戻す条件

「人が最終的に決める」という考え方には沿っています。けれど、**人がボタンを押すことと、機械が安全な状態に戻ったことは別の問題**です。たとえば、戻す条件を次のように組み合わせることが考えられます（改善案で、今の実装ではありません）。

$$
\text{戻してよい} = \text{人の承認} \land \text{センサーが正常} \land \text{揺れが許容範囲} \land \text{必要な点検が済んだ}
$$

ソフトウェアの判定だけで、今ある安全装置や非常停止の機能を置き換えるべきではありません。

### RMS だけでは足りない理由

RMS は信号のエネルギーをおおまかにまとめた値で、周波数の構造は表しません。単純な正弦波 $a(t) = A \sin(2\pi f t)$ なら、周波数 $f$ が違っても振幅 $A$ が同じなら RMS は $A/\sqrt{2}$ で同じです。それでも、運ぶ物の応答は違います。液体には固有の揺れ方があり、容器の形・液の量・加減速のしかたが効きます。

実機では、次の情報を分けて測ります。

- **揺れの強さ**：RMS、最大の加速度、ピークと RMS の比
- **揺れの特徴**：周波数のスペクトル、帯域ごとのエネルギー、急な変化
- **走り方**：速度、加減速、旋回、床の状態
- **載せた物**：重さ、重心の高さ、容器の形、液の量
- **結果**：こぼれ、滑り、転倒、破損、お客さんとの接触の危なさ

大事なのは、こぼれたかどうかだけではありません。**危ないことが起きる前に、どれだけ余裕が残っているか**を測ることです。

## 6. 記録の共有（AT プロトコル）の論点

[`seal.py`](../scripts/guardian_share/seal.py) は、AES-256-GCM、ECDH P-256、HKDF-SHA256 を組み合わせ、宛先の公開鍵ごとに暗号化した記録を作ります。ただし、**中身を暗号化することと、記録があること・共有した履歴を隠すことは別**です。AT プロトコルのふつうのリポジトリは公開のデータを前提にしています。

| 守りたいもの | 今の状態と、これから確かめること |
|---|---|
| 記録の本文 | 今の暗号化で隠す設計 |
| 誰が記録を出したか | DID や公開の記録から推測されうる |
| いつ、どれくらいの頻度で出したか | 公開の場では活動の履歴が見えうる |
| 記録の書き換え | CID で中身が一致するかは確かめられる |
| 記録の削除・欠け | 1 件ずつの中身が正しいことからは、履歴が欠けていないことまでは言えない |
| 鍵をなくしたとき | 読めなくなるおそれがある |
| 鍵が漏れたとき | 過去の暗号文も読まれうる |
| Google Drive への書き出し | AT プロトコルの暗号化とは別の経路で、要約は暗号化せずに同期フォルダへ写す |

記録を前の記録につなぐと、指した記録の書き換えは分かります。けれど、古い記録を見せ直す、途中から別の履歴を見せる、記録ごと消すといったことに備えるには、最新の状態を覚えておく仕組みや、独立した監査の仕組みが要ります。

暗号の方式を選ぶより先に、**誰を攻撃者と考え、何を守り、破られたときに何を保証したいか**を決めることが大事です。

## 7. 研究の問いを数式にする

ここからは、先行研究をもとにした研究のモデルの提案で、今のロボもりに実装したものではありません。目標は「不調でも最大限働かせる」ではなく、**安全と判断できる仕事だけを残し、その範囲で生産性を最大にする**ことです。

ロボット $i$ に仕事 $j$ を割り当てるかを $x_{ij} \in \{0, 1\}$ で表します。いちばん大事なのは、ロボットの状態から見積もる作業の失敗の確率です。

$$
p_{ij} = P(\text{作業の失敗} \mid \text{揺れ・速度・荷物・床・機体の状態})
$$

本当の $p_{ij}$ は分からないので、実験のデータと不確かさを考えた、控えめな上限 $p^{+}_{ij}$ を見積もります。許可は次のように決めます。

$$
a_{ij} =
\begin{cases}
1 & \text{データが有効で、かつ } p^{+}_{ij} \le \epsilon_j \\
0 & \text{それ以外}
\end{cases}
$$

$\epsilon_j$ は仕事ごとの許容リスクです。液体を運ぶ仕事と空いた皿を回収する仕事では、起きる被害が違います。失敗の確率の見積もりだけで実機の運行を許せるわけではなく、衝突の防止、非常停止、速度の制限、機械の安定といった独立した安全の条件は別に要ります。

割り当てには次の制約を置きます。

$$
x_{ij} \le a_{ij}, \qquad \sum_i x_{ij} \le 1
$$

前の式は許されない仕事を割り当てないこと、後の式は 1 つの仕事を二重に割り当てないことです。引き継ぎ中の皿の持ち主の管理は、この変数とは別に扱います。そのうえで、

$$
\min \left[ \sum_{i,j} c_{ij} x_{ij} + \lambda \sum_j u_j + \mu H \right]
$$

を解きます。$c_{ij}$ は実行のコスト、$u_j$ は割り当てられなかった仕事、$H$ は人が手を出す負担です。実際には、通路の取り合いや仕事の順番の制約も加えます。

大事なのは、**危なさを目的関数の罰則として扱わず、許されない行動を最適化の前に外す**ことです。これは、今の固定の表を研究として一般化したモデルです。既存の能力劣化のモデルが「能力が 70% に落ちた」と扱うのに対し、ロボもりは「特定の荷物を安全に運ぶ能力を失った」と見積もります。この違いを実験で示せれば、具体的な貢献になります。

## 8. 実機の実験と、測る指標

論文にするなら、アルゴリズムを高度にする前に、計測と評価を固めます。

| 実験 | すること | 目的 |
|---|---|---|
| 1. 揺れと作業の出来 | 同じロボットで、載せる物・速度・床・重さを変えて走らせる。トレーの上にも基準のセンサーを置き、カメラで滑りと液面の動きを記録する | どの物理量が作業の失敗を予測できるかを見つける（異常検知はまだ目的にしない） |
| 2. 判定のしかたの比較 | 今の 300 mg・連続回数の判定を基準に、RMS だけ、RMS ＋ピーク、周波数の特徴、荷物と床の条件まで入れた判定を比べる | 調整に使っていない床や荷物でも通用するかを確かめる |
| 3. 複数台での配り直し | 異常を模擬で起こし、全部止める方式・今の固定の表・実測のリスクに基づく方式を比べる | 終えた件数に加え、料理の遅れ、引き継ぎの時間、ロボットどうしの待ち、禁止された仕事の実行数を測る |
| 4. 故障と攻撃を入れる | センサーの途切れ、古いデータの再送、センサーの脱落、誤った復帰の操作、通信の遮断を試験の場で再現する | 安全な側へ移るか、戻す条件、記録が欠けないか、関係ないロボットへの影響を確かめる。実際に運用中の機体では行わない |

### 比べる方式

| 方式 | 安全の扱い | 目的 |
|---|---|---|
| 全部止める | 異常の出たロボットを止める | 保守的な基準 |
| 固定の表 | 今の Normal / Warning / Limited の表 | 今のロボもり |
| 条件つきの表 | 荷物・速度・床ごとに許可を変える | センサーを使う効果 |
| リスクの見積もり＋配り直し | 不確かさを考えた許可と割り当て | 提案する方式 |

「不調でも無条件に続ける方式」は、実機の比較の基準には向きません。比べるならシミュレーションの中だけにします。

### 測る指標

| 指標 | 中身 |
|---|---|
| 仕事を続けられた割合 | 異常が起きたあとも、終えられた仕事の割合 |
| 危ない仕事を実行した割合 | 制限すべき仕事が、実行されてしまった割合 |
| 配り直しにかかった時間 | 異常を見つけてから、別のロボットへの割り当てが終わるまで |
| 誤検知の割合 | ふつうの走りを異常と判定した割合 |
| 見逃しの割合 | 危ない状態を正常と判定した割合 |
| 人が手を出した時間 | 確かめる・決める・戻すのにかかった時間 |

### データの量の目安

たとえば、荷物 3 条件 × 速度 3 条件 × 床 3 条件 × 各 10 回なら 270 回走らせます。これは試験計画の例で、統計的に十分という意味ではありません。危ないことがめったに起きない場合は、回数を増やす必要があります。

独立な試行を 300 回して失敗が 0 回でも、「3 の法則（rule of three）」では、失敗の確率の片側 95% の上限はおよそ $3/300 = 1\%$ です。しかも実際の走行は同じ機体や床に依存するので、独立の仮定にも注意が要ります。**300 回事故がなかったことと、安全が保証されたことは同じではありません。**

機械学習を使うなら、同じ走行から切り出した時間の窓を、学習用と試験用にランダムに分けると性能を高く見積もりすぎます。走った日、床、機体、載せた物の単位で分けて確かめます。

## 9. 人とシステムの役割分担

「厳しくするのは自動、戻すのは人」は、安全管理の権限の分け方として分かりやすい原則です。けれど、人に最後の判断を任せれば正しい判断になるとは限りません（Lee & See 2004）。研究では、システムが正しく判断したかだけでなく、**現場の人がその判断を理解できたか、誤った復帰を避けられたか**も評価します。

Parasuraman ほか（2000）の考え方で分けると、次のようになります。

| 処理 | 自動にする候補 | 人の役割 |
|---|---|---|
| 揺れの監視 | 自動 | センサーの点検 |
| 異常の検出 | 自動 | 判断の根拠を確かめる |
| 危ない仕事の禁止 | 自動 | 必要ならさらに止める |
| ほかの機体への配り直し | 安全の制約の中で自動 | 例外への対応 |
| ふつうの状態に戻す | 条件の確認を自動で支える | はっきりと承認する |
| 保守会社への共有 | 要約と暗号化を自動 | 共有先と送ることを承認する |

## 10. 研究開発の進め方

1. **計測が正しいことを確かめる**：センサーの固定のしかた、測る周期、揺れの指標、姿勢と走行の加速度の分け方を確かめ、実機の基準のデータを作る（[Award Day に向けて](../README.md#award-day-に向けて) で作るハードは、この土台になる）。
2. **仕事ごとの許可の条件を実測で作る**：スープ・料理・空いた皿という名前だけでなく、重さ・滑り・容器の形・速度を組み合わせて、安全の制限を導く。
3. **今の方式と比べる**：全部止める方式と固定の表に対して、条件つきの許可でどれだけ仕事を続けられ、どんなリスクが残るかを比べる。
4. **複数台・人・保守をまとめて評価する**：実機とシミュレーションを組み合わせ、配り直し、戻す承認、保守の判断、記録の共有まで含めて実験する。

## 11. まとめ：研究の問い

> **ロボットの状態が不確かで、能力が部分的に落ちているとき、物理的な安全を満たす仕事をどう判定し、複数のロボットにどう配り直せばよいか。**

研究題目の候補は次のとおりです。

- 日本語：外付け慣性センサによる作業能力推定に基づく、安全制約付きマルチロボット動的タスク再割り当て
- 英語：Safety-Constrained Dynamic Multi-Robot Task Reallocation Based on Externally Sensed Task Capability

最初の大きな目標は、機能を増やすことではなく、**どの条件ならスープを運べて、どの条件なら運べないのかを実験で示す**ことです。これが確かめられれば、センサー・判断・配り直しというロボもりの中心の仕組みに、実測の根拠を与えられます。そこから安全の検証、故障時の最適化、工場・物流への展開へと進めます。
